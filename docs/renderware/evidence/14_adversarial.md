## Hard findings and attempted alternatives

### 1. Registered ordering supports temporal reuse, not a same-frame-only zoom filter

- `original/801D2058_DrawBlurTask_Construct.asm:10-14` attaches Draw to render-level object `+0x2c` (index 11); `original/801D20D8_SaveScreenTask_Construct.asm:10-14` attaches Save to `+0x58`. The task vtable execution slots are raw `8053DC84 -> 801D27FC` and `8053DC68 -> 801D2764` (`data_manifest.json:23-52`); those functions call manager Draw/Save respectively (`original/801D27FC_DrawBlurTask_Exec.asm:8-9`, `original/801D2764_SaveScreenTask_Exec.asm:8-9`).
- The raw selector **`804D25D8 = 00000001` is independently read**, not unknown. With the constructor's `index*4+0x5c` lookup (`original/801E4B0C_RenderLevels_Construct.asm:96-102`, VA `801E4C78-801E4C90`), Draw's parent is beneath `+0x60`. Save's `+0x58` parent is explicitly created beneath `+0x64` (`:73-80`, VA `801E4C1C-801E4C38`). `+0x60` is registered before `+0x64` (`:28-53`).
- This is execution order, not merely an inference from phase names: the repeated parent lookup uses the same lazy singleton (`full_disassembly.txt:22319-22345`, `8001C4F8-8001C560`) and index-5 array slot (`:496502-496505`, `801EB614-801EB620`). Base task construction appends to the sibling chain (`:74262-74274`, `8004F094-8004F0C4`); traversal calls `vtable+0xc`, recursively visits children, then follows `+0xc` (`:74069-74083`, `8004ED90-8004EDC8`). Thus the unmodified registered traversal executes Draw before Save.
- The ready byte is tested but **not consumed/cleared by Draw** (`original/8042E254_MotionBlur_Draw.asm:32-34` and entire epilogue `:319-381`). Save clears it on entry and sets it at its tail (`original/8042E838_MotionBlur_SaveScreen.asm:8-17,97-98`). Constructor initializes it to zero on its successful path (`original/8042EA50_MotionBlur_Construct.asm:84-85`). Under one complete enabled traversal per presented frame, the first Draw skips, Save captures, and the next Draw uses the prior traversal's capture.
- **Alternative tested:** EFB copying does occur in the current frame, and the geometry is center-scaled, so same-frame spatial filtering is possible if an external caller invokes Save before Draw. That does **not** describe the registered order just established. Conversely the core has no frame ID, so 'always exactly the immediately previous displayed frame' is too strong if passes are skipped/repeated. The defensible classification is persistent screen-image temporal feedback with optional zoom, conditional on normal scheduling, not velocity/depth-based motion blur or an intrinsic multi-tap radial kernel. One quad submission, primitive 4/count 4, is at `8042E718-8042E738` (`Draw.asm:310-318`); numeric 4 maps to GX `0x98` in `data_manifest.json:117-133`.

### 2. Multiple-camera execution is a concrete counterexample to 'one capture per camera' or 'one Draw per frame'

- Render parent `+0x60` receives vtable `8053EA70` (`full_disassembly.txt:489996-490005`, `801E506C-801E5090`); raw `8053EA7C = 801E4EF0`. Its mode-1/mode-2 branches select a first camera, **explicitly traverse their own children**, then select a second camera (`:489929-489959`, `801E4F60-801E4FD8`; `:489960-489989`, `801E4FDC-801E5050`). The ordinary traversal at `8004EDA8-8004EDB0` then visits these children again after the parent's Exec returns. Draw can therefore execute twice before the later Save parent is reached.
- Save's outer parent `+0x64` has vtable `8053EA54` with raw Exec `8053EA60 = 801E4E40`. That routine resets camera selectors to zero before children (`full_disassembly.txt:489857-489882`, `801E4E40-801E4EA4`). Draw uses one object raster at `+0x74`, resolves the current camera afresh, and derives UV bounds from that camera's raster dimensions/offset (`Draw.asm:16-34,91-109,173-186,241-253`). Save also resolves the current camera afresh (`SaveScreen.asm:18-33`). There is no capture-camera identity or per-camera history array in this core.
- **Alternative tested:** this need not be erroneous cross-camera contamination: a single full-screen history atlas can intentionally hold multiple view regions, with per-view UV cropping. But one cannot replace it with independent camera histories or claim capture/draw camera equality. Runtime camera/raster dimensions and skip flags still determine which regions are reused.
- **Feedback caveat:** the first Save copy reads the then-current EFB, after the earlier registered Draw (`SaveScreen.asm:34-39`); the second copy reads the temporary small-quad result (`:69-81`). There is no clean pre-blur-scene buffer in the effect. If earlier compositing survives intervening work, the next capture contains the already blended image, i.e. recurrence/feedback, not just the previous *unblurred* scene. Intervening clears/overwrites can defeat that recurrence; this is a conditional mechanism, not an observed all-scenes trace.

### 3. `ready` means a control path was reached, not that both render passes succeeded

- Save invokes the full-screen copy **before** its first BeginUpdate (`SaveScreen.asm:34-43`, `8042E8AC-8042E8D0`). First BeginUpdate failure branches to `8042E960`, not to the function exit. The second copy and second BeginUpdate still occur (`:79-85`). Second BeginUpdate failure branches to `8042E9A8`, which stores ready=1 (`:97-98`). Copy/draw/end return values are not checked.
- **Exact counterexample:** camera resolution succeeds but both BeginUpdate callbacks return zero. Both copies are attempted, neither quad is drawn, and ready becomes 1. The second copy then captures a top-left half-sized EFB region without the intended geometric downscale. Calling this byte `lastCaptureSucceeded` would overstate its semantics.
- **Second counterexample:** first BeginUpdate fails, second succeeds. The only texture bind and ONE/ZERO changes are in the skipped block (`8042E8D4-8042E930`, `:44-67`); the second quad (`:86-96`) therefore uses inherited texture/blend state, not necessarily the full-screen backup texture. Moving the bind outside that conditional or making both passes transactional changes original behavior.
- **Alternative tested:** production camera callbacks may never fail with valid initialized cameras. These are proven branch behaviors, not a claim that the game has been observed taking them. They still forbid 'every return with ready=1 is a successful capture' or an unqualified fault-faithful reconstruction claim.

### 4. Actual 0x505 allocation supports alpha-bearing RGBA8; alpha/255 is not an unconditional effective weight

- Constructor requests `0x505` for both raster allocations (`Construct.asm:354-382`, `8042EFC4-8042F034`), depth argument zero. The wrapper forwards flags to the backend callback (`full_disassembly.txt:1184182-1184200`, `8048AF14-8048AF5C`). The raw standard-function record is `8051D448: 00000004, 80497CA8`; its installer is `804954F8-804955F0` (`full_disassembly.txt:1194799-1194861`). Backend create directly calls `80497458` (`:1197367`); the `0x500` format branch (`:1196948-1196949`, `8049768C-80497690`) reaches `80497884-80497898` (`:1197074-1197079`), storing **GX format 6, depth 32, alpha flag 1**. This is not a justified RGB565/opaque-texture-only shortcut.
- Copy's texture-format argument is loaded from root extension `+0xc` (`original/80496208_RwRaster_CopyEFB.asm:43-49`). Both calls from Save pass copy's second argument zero; that is the half-size/source-scaling control at `8049624C-804962A0`, **not the clear flag**. Actual GXCopyTex clear is low byte of global `805F2688` (`CopyEFB.asm:109-114`, `804963A8-804963BC`). A hardcoded clear=false copy abstraction loses a real global dependency.
- Draw's requested RW factors 5/6 (`Draw.asm:255-269`) map to GX source-alpha/inverse-source-alpha 4/5 (`data_manifest.json:94-114`; `original/80498954_RwRenderState_Set.asm:269-280,299-308`). Its vertex color is white with byte alpha from parameter `+1` (`Draw.asm:187-212`), and the emitter really sends RGBA bytes (`original/80491E80_Im2D_RenderPrimitive.asm:42-59`). These *requested* factors and vertex bytes are validated.
- Im2D calls TEV operation 0 (`original/8049148C_Im2D_Prepare.asm:61-63`). Independently read raw color/alpha combiner words are `80568B00=C008F8AF`, `80568B28=C108F2F0`; `803992EC-80399370` installs them (`full_disassembly.txt:936620-936653`). With identity swap tables these decode to texture color times raster color and **texture alpha times raster alpha**. The unquantized equation is `Cout = As*Ctex + (1-As)*Cdst`, with `As = Atex*(alphaByte/255)`, conditional on surviving tests and enabled color writes. Exact TEV/EFB rounding is not established by that idealized equation.
- **Exact alternative input:** alphaByte=128 and captured texture alpha=0 gives zero source-alpha contribution (or alpha-test rejection), not 128/255 weight. Opaque captured alpha is plausible when the active EFB format supplies alpha=1, but requires EFB-format/content evidence, not inference from the byte setter. `0x505` itself does not force Atex=1.
- **Additional inherited-state blocker:** GXSetTevOp preserves the low four alpha-combiner bits (swap selectors), rather than resetting them (`80399358-80399368`, `full_disassembly.txt:936648-936652`). Im2D does not reset swap selectors/tables in its shown setup. The simple modulation equation must assume identity swaps, not claim arbitrary-state immunity. Texture alpha flags also switch alpha-test/Z-compare-location behavior through `80498890-804988F4` (`original/80498854_RwTexture_FlushState.asm:20-45`).

### 5. Save is not a pure state-preserving copy; Draw restores only its listed subset

- Save sets only texture raster and RW blend IDs 10/11, then draws twice, without saving/restoring them (`SaveScreen.asm:44-96`). Capture filter, address modes, depth/fog, color/alpha writes, scissor and alpha compare are not all established by the effect. Im2D sets vertex/TEV/projection/viewport state, but that does not establish all these other states (`original/8049148C_Im2D_Prepare.asm:5-190`).
- Draw requests states 10,11,12,6,8,14,9; requests changes to raster 1 and those seven states; issues seven matching restore requests but **never restores raster 1** (`Draw.asm:35-90,246-318,319-376`). ID12 is unsupported, as detailed below. An RAII 'restore every GX/RW state' implementation is a deliberate behavioral change.
- Filter counterexample is concrete: RW filter ID 9 changes only the low byte of cached texture `+0x50` (`original/80498954_RwRenderState_Set.asm:175-180`, `80498BFC-80498C10`). Draw chooses 1 and restores prior 9 afterward (`Draw.asm:302-309,367-374`); Save never chooses 9. Independently read pairs at `8056FC98/9C=(0,0)` and `8056FCA0/A4=(1,1)` map filter 1 to GX nearest and 2 to GX linear. Texture realization uses the pair selected by that cached value (`full_disassembly.txt:1200801-1200835`, `8049B2C0-8049B348`). An incoming nearest state versus linear state can change capture pixels: **intrinsically bilinear downsampling is not proven**, even though the capture quad halves dimensions.
- **Alternative tested:** normal render tasks may establish a known benign state before Save. That is a pipeline contract, not a property of Save itself. Counterexamples using color writes disabled, restrictive alpha compare, or stale texture binding demonstrate missing local guarantees; they are not observed runtime failures.
- State **12 is an especially important non-operation** here. Raw get-table entry `8056FA88=804986B0` returns false without writing the output (`original/804984C4_RwRenderState_Get.asm:128-129`); set-table entry `8056FB04=80498F58` is the failure/default (`data_manifest.json:136-176`; setter `:8,390-396`). Draw ignores get failure, then loads stack `+0x1c` to restore this unsupported state (`Draw.asm:51-58,335-342`). There is no supported 'vertex-alpha enable' cache to invent. In a literal C++ port, an ordinary uninitialized `int state12` read is C++ UB even though the PPC setter ignores its value; preserve/document the failed request without claiming a deterministic saved value.

### 6. Setters do not clamp scale or canonicalize enable; instruction-level float rounding matters

- Both assignment helpers copy byte 0, byte 1, float `+4`, and words `+8/+0xc`, with no comparison/clamp (`original/8042E9F0_MotionBlur_AssignParameters.asm:5-15`, `original/8042EA1C_MotionBlur_AssignParametersIfPresent.asm:5-17`). The latter alone skips a null source. Getter uses the same fields (`original/8042E9C4_MotionBlur_CopyParameters.asm:5-15`). Padding `+2/+3` is not part of those copies.
- **Counterexamples:** enable byte 2 survives a round trip, whereas converting the field to canonical C++ bool changes it. Scale 0 produces a degenerate center quad; scale below 1 shrinks rather than expands. NaNs/infinities are not locally rejected. Caller-side validation may restrict ordinary inputs but cannot be attributed to these core setters. Words `+8/+0xc` have no demonstrated blur-draw role; do not invent sample-count/velocity meanings.
- The margin is computed by separate single-precision instructions: `fsubs(scale,1)` at `8042E5A4`, width/height `fmuls` at `8042E5AC/B4`, then multiply by 0.5 at `8042E5C0/C4`, then separately add dimension at `8042E5DC/E4` (`Draw.asm:214-240`). Rewriting as `(scale*W-W)/2` is not bit-equivalent.
- **Executed in-memory RN32 counterexample:** scale bits `3f800001` (1.0000001192092896), W=640. Original margin bits `38200000` = 0.00003814697265625; right edge bits `44200001` = 640.00006103515625. Reassociated margin bits `38000000` = 0.000030517578125; right edge bits `44200000` = 640. This is an arithmetic test, not PPC execution. Half-integer UV addition and `fdivs` also need their original ordering; fast-math/FMA reassociation cannot be called instruction-faithful by syntax checking.
- Constructor halves signed dimensions with `srawi; addze` (`Construct.asm:256-263`, `8042EE3C-8042EE58`), truncating toward zero, not generic unsigned right-shift or necessarily floating half. Real positive dimensions may hide the distinction.

### 7. Invalid construction and returned stack residue cannot be silently 'fixed' while claiming exact fidelity

- Constructor's early no-wrapper/no-camera exits at `8042EAA4-8042EAD0` occur **before** history pointer `+0x74` and ready byte `+0x78` initialization at `8042EB8C/90` (`Construct.asm:26-37,84-85`). Initial writes cover enable=0, alpha=0, scale=1, manager pointer (`:8-17`), not a zero-filled whole object.
- Create nevertheless stores the allocated object in manager `+0x40` (`original/8042F20C_MotionBlur_Create.asm:11-18`). Destroy loads `+0x74` and dereferences it if nonzero (`original/8042F198_MotionBlur_Destroy.asm:14-24`). **Counterexample:** no camera at construction plus nonzero recycled heap contents at `+0x74`; subsequent Destroy can follow a stale pointer. There is also no core checking of the two raster-creation or subraster-attachment results (`Construct.asm:372-382`); wrapper/backend failure paths do exist (`full_disassembly.txt:1184200-1184218`, `8048AF5C-8048AFA4`; `original/8048AE14_RwRaster_SubRaster.asm:12-16,36-42`).
- **Alternative tested:** callers may enforce camera/allocation preconditions, and fresh heap pages may happen to contain zero. No actual crash has been reproduced. A safer reconstruction may initialize/check these values, but must label this normalization and exclude invalid-path equivalence.
- GetParameters when **`manager->blur == nullptr`** (not when the manager itself is null) explicitly reads **unwritten stack words** `+0x10/+0x14` and stores them to returned fields `+8/+0xc` (`original/8042F084_MotionBlur_GetParameters.asm:15-24`, `8042F0AC-8042F0D0`). This is neither 'zeros', nor 'preserve caller's old words', nor a determined default pair. Successful construction with null initial parameters similarly only sets 0/1/4 at `8042F050-8042F068` (`Construct.asm:389-395`). Portable deterministic defaults are adaptations, not facts from the DOL.
