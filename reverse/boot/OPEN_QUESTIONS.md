# Native boot frontier — PAL GUPP8P

These are the next proof obligations after the buildable register-startup slice.
`PROVEN` means directly checked against the PAL DOL or SYS bytes; `UNKNOWN`
means the present public evidence does not settle the runtime result. Do not
turn an unresolved value into a default in native code.

| Priority | Question | Current evidence and boundary |
|---|---|---|
| P1 | What guest-visible state is established before DOL entry `0x80003154`? | `research/PREENTRY_STATE.md` and `research/APPLOADER_PATH.md` check disc/apploader instructions. `research/ASM_HARDWARE_VALIDATION.md` records a verified startup-only Dolphin/HLE run with `[0x80000028]=0x01800000`, FST base `0x817E74E0`, and zero FPR source bytes. **UNKNOWN for retail IPL:** its low-memory word, selected FST placement/order and complete pre-entry register/memory image. Keep the HLE oracle conditional. |
| P1 | Which effects of `0x80003400` must survive native translation? | The raw notes check the bounded words. Native C++ applies two validity-tracked BE32 stack stores, issues HID2/HID0 requests and stops before sync at `0x80371730`. `research/HIDDEN_BOOT_STATE_36.md` now measures HLE cache reset/refill, GQR/HID2 readback and both FPR lanes; an unconnected 74-word native FPR projection matches six controlled runs. **UNKNOWN:** retail inputs, physical cache/barrier consequences, exceptional FP behavior and connected parity beyond sync. |
| P1 | What does the HID0 `0x800` write mean? | **PROVEN bytes/ISA:** `0x803725F8/FC` OR/write ICFI, self-clearing with ICE enabled. **OBSERVED HLE:** issued `0011CC64`, separate readback `0011C464`; single-stepping the command clears all 128 cache-valid and replacement bytes at `80372600`, then fetches refill them. `HIDDEN_BOOT_STATE_36.md` also identifies an HLE/manual ICE=0 difference. **UNKNOWN:** retail timing and the precise native completion replacement. |
| P1 | What is required to cross `sync` at `0x80371730`? | `research/ICFI_SYNC_BOUNDARY.md` independently checks the instruction and manual: a request log alone cannot establish completed ICFI, instruction visibility or bus ordering. HID0[ICE]=0 and [ABE]=1 are counterexamples to a universal no-op barrier. `research/SYNC_GQR_CHAIN.md` checks the following 14 words and eight GQR writes, but **native remains stopped before sync** until a completion/readback service and downstream comparison are validated. |
| P1 | Can a raw-code fingerprint establish what the GQR tail does at runtime? | The 14-word pattern and conditional `PredictPostSyncGqrTail()` are checked in checkpoint 35. Checkpoint 36 independently reads all eight GQRs as zero at `80371758` and the first paired consumer `80370CFC`. Initial HLE GQRs were also zero, so binary/ISA evidence supplies the write order. **UNKNOWN:** physical acceptance/timing and native ICFI/sync completion. Connected frontier remains `80371730`. |
| P1 | What is the paired FPR PS1 state? | `research/HIDDEN_BOOT_STATE_36.md` exposes both lanes in one run: distinct `1.5/-2.25` paired inputs become `3FF8000000000000/C002000000000000`; the sweep copies both, then lfd/fmr replace PS0 with a distinct scalar while PS1 survives. Six HLE cases match 4,896 fields in the bounded native projection. A reproduced reserved FPSCR bit bug is fixed and regression-tested. **UNKNOWN:** physical internal format, retail source bytes, skipped paired edge, subnormal/nonfinite semantics and connected execution. |
| P1 | When and how are CRT zero/copy tables applied? | **PROVEN bytes:** `research/BINARY_CRT_PREFIX.md` checks 111 instruction words and 41 descriptor words; `CRT_MEMORY_EXECUTION.md` resolves three reached zero fills and corrects final r4/r31 with an HLE return comparison. The DOL header BSS envelope overlaps initialized data6/data7. **UNKNOWN:** original pre-entry writes, any descriptor mutation and connected native CRT parity. Never blanket-zero the header envelope. |
| P1 | Which constructors and indirect targets run before application setup? | **PROVEN static:** text0 calls the event-loop wrapper `0x800510C0`, after constructor walker `0x803796CC`; its recurring phase is mapped in `research/APPLICATION_LOOP.md`. `research/CRT_TO_GAME.md` counts 282 in-text constructor targets; `CONSTRUCTOR_NEXT_TARGETS.md` covers body effects for indices 12–15 after the earlier 0–11. **UNKNOWN:** original runtime order/results of constructors and OS initialization, indices 16–281, first event/frame reachability, and complete dispatch effects without a trace. `experimental_native_boot/` is reference-only. |
| P1 | Are the 15 structurally clustered constructor-table targets one semantic family? | Batch 1 found a minimum pair structural score 0.8036 across `ctor_16`–`ctor_26`, `ctor_28`, and `ctor_32`–`ctor_34`; `ctor_16` has four ordered stores at `0x8005C76C..0x8005C77C`. **UNKNOWN:** live writable table contents, source SDA/SDA2 values, object ownership, and entry/return memory delta. Compare a live dispatch and before/after state before classifying or connecting any of them. |
| P1 | Do the eight normalized-identical multiword constructor bodies execute with the same values? | `research/SEMANTIC_RECOGNIZER_33.md` checks indices 135/141/143/145/147/149/151/155 against distinct raw words, one normalized 58-word pattern, the common three-word source `0x80514CB8..C0`, and 24 concrete destination addresses each. **UNKNOWN:** live constructor-table pointers, source bytes at dispatch, ordered writes and later consumers. | P1 | What are the NPC MotionImpl three-word entries and how are they consumed? | `research/MOTION_TABLE_CONSTRUCTORS_34.md` proves the eight-body 13-entry copy graph and ties each data area to matching original RTTI `Player::Npc::<character>::MotionImpl` vtables and code pointers. | P1 | Which clock and low-memory inputs feed the first OS call? | `research/OS_ENTRY_NEXT_BOUNDARY.md` independently checks 63 instruction words: the first-call guard follows the CRT zero interval; the helper samples stable TB high/low/high, adds BE32 words at `0x800030D8/DC` with carry, restores prior EE, and stores the result low word before high. **UNKNOWN:** retail TB, low-memory offset producer, interrupt/device consequences and connected native OS entry. |
| P1 | Can L2 status polls be simplified? | `research/L2_STATUS_ORACLE.md` captured both L2IP reads as zero on one synthetic run, with a guest L2I clear between them. The two loops reread live L2CR; retail timing, cache tags and nonzero-status paths are **UNKNOWN**. Keep both polls and the logger branch explicit. |
| P2 | How should disc lookup be represented after boot? | **PROVEN:** the original FST has 3,615 entries (see `BOOT_PROCESS.md`). Native `assets/` has FST/ONE readers. **UNKNOWN:** full game-observed DVD ABI behavior, async completion and offset identity; these remain separate from the bounded entry proof. |

The next implementation should extend one proven original branch or service
with a fixture fingerprint and focused negative tests, then run the full root
CTest gate. A playable or fully boot-equivalent claim requires later runtime
and pixel gates; the current boot probe is only the first entry transition.
